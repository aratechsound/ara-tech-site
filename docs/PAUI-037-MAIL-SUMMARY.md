# PAUI-037 semantic email summary candidate

Status: HOLD for provider activation and real semantic-quality evaluation. PAUI-036 is the exact parent. No Production publication is authorized.

The site source and documentation contain no approved customer-email semantic AI integration. A PC coding-agent subscription is not evidence of authority to send customer email through a new API. Production AI environment configuration, account entitlement and spend limits were not accessed. No new credential, paid subscription or customer-data transfer was created.

The candidate provides the semantic prompt, full-body input, structured response validation, provider adapter, authenticated handler, cache contract and list UI. It never labels excerpts as AI summaries. The existing excerpts are explicitly labelled original text. The original/full-body/quotation and attachment paths remain available. States distinguish not generated, loading, failure and successful summary; the UI uses textContent for all model output.

The existing `/api/pa-gmail` function gains an isolated `mail_summary=1` selector. Its GET reads status and cached summaries only. An explicit same-origin POST requests generation. The workspace adapter stays GET-only and reuses normal Owner JWT, work_admins, inquiry readability, approved thread, index conflict and Gmail message/thread binding checks on every read, including a cache hit. Browser input supplies identity only; source text, direction, attachment names and verified Owner identity come from the authenticated server read. No service-role access, Gmail label changes, sync, link mutation or commercial action is added.

Two visible summary requests may run concurrently; the list never awaits them. There is no background generation or automatic paid retry. Private frontend state is bounded to 200 entries, partitioned by case/thread/message/source metadata and discarded at sign-out/page exit/latest-mail refresh. Case epochs prevent late results from entering another case. Full source bodies never enter logs or persistent browser storage.

Server keys bind verified Owner, inquiry, thread, message, complete source document hash, prompt version, provider and model. A supplied durable cache must implement get, atomic claim and complete. The claim must survive process failure, have no automatic lease expiry/retry, and preserve failed/unknown outcomes until explicit operator reconciliation. Cache failures prevent dispatch. A timeout or invalid response becomes terminal for that key; reading/reopening cannot dispatch again. Token refresh does not change Owner identity. A process-local Map is only a test double, not a deployed durable cache. This repository has no approved durable cache adapter; it is deliberately not enabled and no migration is introduced.

POLICY.enabled is false. Environment values and UI requests cannot turn it on. Activation requires a separately reviewed exact source change after Owner approval of provider/model, data handling, authentication, spending limits and durable-cache integration. The sample OpenAI Responses transport is never instantiated by the default handler. It sends the complete plain-text email, subject, direction and attachment filenames, with tools absent, store:false, truncation disabled and a timeout. HTML-only or oversized/empty messages are left ungenerated rather than truncated, replaced with snippets or incompletely summarized. Attachments themselves are not sent or interpreted. The prompt reads long quotations as historical context, preserves requests and uncertainty, and asks for evidence spans; evidence validation and numeric checks do not prove completeness, meaning, chronology or hallucination freedom.

OpenAI API calls would incur usage charges separate from the coding-agent session. No model or price is selected, so a per-mail cost cannot honestly be quoted yet. Before activation, select a model and calculate input tokens (full body including quotes), output tokens and daily/mail limits using its current tariff; enforce the approved budget through the durable provider/cache integration. Alternatives are an approved existing internal AI endpoint or a self-hosted semantic model; neither is currently verified. Keeping the feature ungenerated costs no AI usage and is the present behavior.

The architecture was checked against official OpenAI documentation on 2026-10-14: [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [Data controls](https://developers.openai.com/api/docs/guides/your-data). `store:false` disables response application storage; it does not establish a zero-data-retention agreement or remove all provider retention obligations. Owner must approve the actual account's controls.

Tests A-J use invented non-confidential mail and hand-authored provider doubles to check full-source delivery, rendering and input/output fidelity. They are not actual model-quality results. K checks failure/timeout/no-retry; L checks 500 rows, bounded concurrency and case switching. Security tests exercise the real Owner/ACL/source handler with fictional upstreams. All pre-existing tests and the PAUI-036 UNKNOWN helper remain preserved. Actual AI quality A-J, omission/false-certainty resistance, provider latency/cost, approved persistent cache and Production Owner/Gmail acceptance remain HOLD for a separate authorized task.
