# ARA-TECH WORKS publication

Read [the operational contract](../../../docs/UPCOMING_EVENT_CODEX_WORKFLOW.md) and [API and evidence reference](references/api-and-evidence.md). Explicit invocation: `$ara-works-publish`. Automatic selection is enabled; instructions never grant authentication or publication authority.

## Scope and authorization

Record the Owner instruction, exact event identity or existing work IDs, intended fields and image decision. A general request to add an event authorizes research/candidate preparation only. An explicit instruction to formally publish a specified event authorizes autonomous continuation through the existing administrator API, including image approval, after matching all current content to that instruction. Do not require a second GO or an OK dialog. Never inherit approval for unrelated works. Changed or conflicting content stops mutation until reviewed; original scope may still authorize corrections that implement the exact requested content.

## Execute

1. Read current Production schema, target rows and classifications. Search date, performer, venue and title including pending/draft records. Reuse one matching candidate; if multiple matches exist, HOLD without INSERT. Preserve baseline hashes of unrelated WORKS and relevant Storage objects. Do not touch PA/Gmail data.
2. Verify event identity and labeled OPEN/START against venue/organizer/artist official sources. Preserve conflicts. Use existing `scripts/add-upcoming-event.mjs` for local research/candidate/review artifacts when creating a candidate. For an existing reviewed candidate, reuse it and its images/body; do not regenerate or reinsert.
3. Separate technical image availability, Owner publication direction and third-party permission evidence. Never invent permission. Verify source correspondence, MIME, signature, size (maximum 10 MiB), decoding and SHA-256. Upload only through existing authenticated `work-flyers` Storage API; use a new permanent path, never overwrite/delete old images. Read saved bytes and match SHA. Reuse verified existing Storage images without upload. Record provenance and use existing image confirmation/audit fields.
4. Use an existing authorized administrator runtime with `client.auth.getUser()` and a successful `work_admins` membership check under RLS. Do not export browser tokens/passwords or use service_role, postgres, SQL mutation, auth.uid impersonation, new gateways or authentication bypass. A management connector's SQL access is readback authority, not administrator publication authority. If no supported authenticated execution surface exists, record exactly that missing prerequisite; skill installation cannot supply it.
5. Prefer `scripts/publish-reviewed.mjs` with the runtime's existing Supabase client, exact reviewed pin, Owner instruction reference and authenticated actor ID. This helper accepts already stored images and makes no INSERT. Use existing upload/registration API separately if needed. Never broaden old `WKS001_IDS` or reuse that fixed ten-item button. No automatic browser publish-button/dialog clicking. No direct `is_published` UPDATE. The final mutation is only `publish_work_candidate(p_work_id, p_candidate_hash)` after fresh read and image checks. Retain image audit and approval actor/time; a changed hash fails closed.
6. If a publication response is UNKNOWN, read the same row before any further action. Do not automatically repeat the RPC. Already formally published rows are skipped. A database state alone does not establish public display PASS.
7. Read Production independently: published state, pending cleared, latest approved_hash=candidate_hash, approved actor/time, image confirmation actor/time and image audit. Get the actual slug/URL from DB/site; verify HTTP200, canonical/title/OGP, Event JSON-LD, official link, sitemap and stored-image hash. Check PC and mobile real rendered content, image decoding and overflow; save screenshots. Recheck unrelated baseline rows and images. Missing verification remains HOLD.
8. Save `outputs/<TASK_ID>/RETURN.md` and `EVIDENCE.json` before Return. Report skill installation/discovery, publication, image, PC/mobile, preservation, Bridge/cloud, browser delivery and formal ACK independently. Use existing report Publisher with sanitized RESULT.json/REPORT.md only: verify the configured Drive root, dry-run, then copy only if dry-run PASS. Cloud readback is separate. Never enable retention or create Return infrastructure.
9. With explicit Return destination authorization, use the existing Edge browser Return method. Independently match complete URL, Project, conversation ID and WKS content; require an empty composer, idle answer and no competing browser operation. Send the recorded result once, even if work is HOLD. After UNKNOWN, read the same conversation; never resend or reroute. Confirm exact new user message, new reply marker and answer completion, plus the available independent conversation readback. Stale independent history means strict BROWSER_RETURN=HOLD even if visible receipt passed. Formal ARA OS ACK stays UNVERIFIED without its own proof. A publication browser failure does not automatically block a separately verifiable Return destination.
