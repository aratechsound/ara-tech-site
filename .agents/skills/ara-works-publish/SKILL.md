# ARA-TECH WORKS publication

Read [the operational contract](../../../docs/UPCOMING_EVENT_CODEX_WORKFLOW.md) and [API and evidence reference](references/api-and-evidence.md). Explicit invocation: `$ara-works-publish`. Automatic selection is enabled; instructions never grant authentication or publication authority.

## Scope and authorization

Record the Owner instruction, exact event identity or existing work IDs, intended fields and image decision. A general request to add an event authorizes research/candidate preparation only. An explicit instruction to formally publish a specified event authorizes autonomous continuation through the existing administrator API, including image approval, after matching all current content to that instruction. Do not require a second GO or an OK dialog. Never inherit approval for unrelated works. Changed or conflicting content stops mutation until reviewed; original scope may still authorize corrections that implement the exact requested content.

## Route by observed capability

At startup, probe GitHub access, read-only Production DB, local files, PC browser, restored WORKS administrator membership, authenticated API execution and authorized Browser Return. Record observations using [the runtime reference](references/cli-api-runtime.md). A Cloud runtime may publish if its existing authorization and execution surface are verified. If neither the existing PC browser panel nor a supported same-session API is available, prepare the reviewed candidate, duplicate-check evidence and PC handoff under the original task ID. Recheck the live row and pin its DB hash before any write.

## Execute

1. Read current Production schema, target rows and classifications. Search date, performer, venue and title including pending/draft records. Reuse one matching candidate; if multiple matches exist, HOLD without INSERT. Preserve baseline hashes of unrelated WORKS and relevant Storage objects. Do not touch PA/Gmail data.
2. Verify event identity and labeled OPEN/START against venue/organizer/artist official sources. For multiple parts with one OPEN/START pair, store part 1 in the fields and preserve each subsequent part and its times in the public description. Preserve conflicts. Use existing `scripts/add-upcoming-event.mjs` for local research/candidate/review artifacts when creating a candidate. For an existing reviewed candidate, reuse it and its images/body; do not regenerate or reinsert.
3. Record the Owner’s exact image selection (source, SHA-256 and instruction reference), third-party permission status and verified placement separately. Use the existing Owner instruction as the editorial decision. Record unverified third-party permission as unknown without requiring an additional search or approval. If an explicit usage prohibition or access restriction applies, stop the image action and record the concrete restriction. Do not substitute another image or proceed without the selected image unless explicitly directed. Match the official event and verify HTTP, MIME, signature, size (maximum 10 MiB), decoding, dimensions and SHA-256. Upload by the authenticated work-flyers Storage API with a new path, and verify saved bytes against the selected hash. Reuse a matching staged image. Preserve existing objects.
4. Use an existing authorized administrator runtime with `client.auth.getUser()` and a successful `work_admins` membership check under RLS. Do not export browser tokens/passwords or use service_role, postgres, SQL mutation, auth.uid impersonation, new gateways or authentication bypass. A management connector's SQL access is readback authority, not administrator publication authority. If no supported authenticated execution surface exists, record exactly that missing prerequisite; skill installation cannot supply it.
5. Prefer the existing authenticated WORKS admin panel when official PC browser controls are verified. Match the Owner's explicit instruction, current event, image choice and candidate hash, then advance the five steps and activate the matching publication action once. If the panel cannot be operated, use `scripts/publish-reviewed.mjs` through a supported app surface in the same session with the exact reviewed pin, Owner instruction reference and authenticated actor ID. The helper accepts already stored images and makes no INSERT. Never reuse the historic fixed ten-item button. The final mutation is only `publish_work_candidate(p_work_id, p_candidate_hash)` after fresh read and image checks. Retain image audit and approval actor/time.
6. For an image-only addition to a published WORKS row, use the authenticated edit form’s 画像だけ追加 action. Supply the existing Owner instruction reference, exact SHA-256, provenance and actual rights status. Preserve the row’s public state, work content and original formal approval. Use the formal publication RPC only for pending candidates. On an ambiguous response, read the same row before proceeding and reuse the matching staged object. Never automatically retry the formal publication RPC.
7. Read Production independently: published state, pending cleared, latest approved_hash=candidate_hash, approved actor/time, image mode and, when included, image confirmation actor/time and image audit. Get the actual slug/URL from DB/site; verify HTTP200, canonical/title/OGP, Event JSON-LD, official link, sitemap and stored-image hash when used. Check PC and mobile real rendered content, image decoding and overflow; save screenshots. Recheck unrelated baseline rows and images. Missing verification remains HOLD.
8. Save `outputs/<TASK_ID>/RETURN.md` and `EVIDENCE.json` before Return. Report skill installation/discovery, publication, image, PC/mobile, preservation, Bridge/cloud, browser delivery and formal ACK independently. Use existing report Publisher with sanitized RESULT.json/REPORT.md only: verify the configured Drive root, dry-run, then copy only if dry-run PASS. Keep a HOLD result local. Check cloud synchronization and ChatGPT readback independently. Never enable retention or create Return infrastructure.
9. With explicit Return destination authorization, use the existing Edge browser Return method. Independently match complete URL, Project, conversation ID and WKS content; require an empty composer, idle answer and no competing browser operation. Send the recorded result once, even if work is HOLD. After UNKNOWN, read the same conversation; never resend or reroute. Confirm exact new user message, new reply marker and answer completion, plus the available independent conversation readback. Stale independent history means strict BROWSER_RETURN=HOLD even if visible receipt passed. Formal ARA OS ACK stays UNVERIFIED without its own proof. A publication browser failure does not automatically block a separately verifiable Return destination.

## Existing session reuse (WKS-004 Owner correction)

Read [references/cli-api-runtime.md](references/cli-api-runtime.md). Reuse the authenticated WORKS session in `admin.html`. If absent or expired, let the Owner sign in at the official site, then recheck the administrator identity and membership. Supabase Dashboard OAuth uses a separate session. Do not extract browser credentials or create a new credential store. The shared admin panel calls `js/work-reviewed-publish.mjs` with the existing client and shows the public URL after DB readback. Normal administrators can use all five steps manually. Codex can use those same steps with prior explicit Owner approval for the matching candidate and verified official PC browser input. Continue independently authorized Return even when publication is HOLD.

For an image-only edit, report PUBLICATION_RESULT, IMAGE_RESULT, Storage verification and public detail/list/OGP evidence separately. Compare the rendered image to the exact pin and inspect desktop and mobile for clipping or distortion. Continue Browser Return when any work component is HOLD.
